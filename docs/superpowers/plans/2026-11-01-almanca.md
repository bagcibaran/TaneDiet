# German language and server message translation: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** add German (TR/EN/DE) to the whole app, and show server error messages in the user's language.

**Architecture:**
- The frontend gets a full `de.json`, a third language button, a locale key checker, and a `serverErrors.json` map (Turkish server message → en/de) used by `toErrorMessage`.
- The backend adds German legal texts and a guard test that every user-facing server message has a translation.

**Tech Stack:** React 19, i18next, Spring Boot, JUnit 5.

**Spec:** `docs/superpowers/specs/2026-11-01-almanca-design.md`

## Global Constraints

- **German register:** clients are addressed with **du**, dietitian-only strings use **Sie**.
- **Never translated:** "tane.", "Dyt. Betül Bağcı" and "KVKK". KVKK is explained once as "KVKK (türkisches Datenschutzgesetz)".
- **Language codes:** normalise to two letters (`de-DE` → `de`).
- **Server code:** unchanged except the legal texts. Server messages stay Turkish.
- **Frontend checks:** `npm run build`, `npm run lint` and `npm run check:locales` must be clean.
- **Backend checks:** the unit suite (`.superpowers/suite.txt`; add new test classes to it) and `ProjectApplicationTests`.
- **Rules:** never run `mvnw clean`; the user commits; end-to-end checks run on :8081/:5174.

## Review Focus

1. **German text is long:** buttons and tab labels must not overflow at 360–375 px (tab bar, diet editor, language toggle row).
2. **Plural keys:** German uses `_one` and `_other` like English. Every `_one`/`_other` pair in `tr.json` exists in `de.json`.
3. **Server message prefix matching:** a dynamic message such as `"Danışan bulunamadı, id: 41"` must match the prefix entry and drop the id. An unknown message is shown as-is.
4. **A missing German legal text must not break consent:** the version is the same, so accepting in German records the Turkish version.
5. **Language detector:** a browser set to `de-AT` gets German, and the toggle highlights DE.

### Task 2: Server message translation

**Files:**
- Create `client/src/i18n/serverErrors.json`.
- Modify `client/src/services/errorMessage.ts`.
- Create `project/src/test/java/com/project/project/ServerMessagesTranslatedTest.java`.

**Interfaces:**
- `serverErrors.json`: `Record<string, { en: string; de: string }>`. Keys are the exact Turkish messages. Keys of dynamic messages end with the static prefix, e.g. `"Danışan bulunamadı, id: "`.
- In `errorMessage.ts`, `translateServerMessage(message: string, language: string): string`:
  1. if the language is `tr`, return the message;
  2. otherwise try an exact key;
  3. then the longest key that the message starts with;
  4. otherwise return the message as-is.

  `toErrorMessage` uses it with `i18n.language` (from the `t` function's `i18n` or the i18n import).

- [ ] **Step 1: Guard test.** Scan `src/main/java` for messages:
  - `new \w+Exception\(\s*"..."` (the literal up to the closing quote, allowing a newline after the parenthesis);
  - `message = "..."` (validation annotations and the handler);
  - `MESSAGE = "..."`.

  Excluded:
  - `AccessDeniedException` messages;
  - the `TaskNotFoundException` messages and the `TaskService` file;
  - log calls.

  The test reads `../client/src/i18n/serverErrors.json` and asserts every message has non-empty `en` and `de`. When the file does not exist, use `Assumptions.assumeTrue`. On failure, list the missing messages.
- [ ] **Step 2:** Run the test. Expected: FAIL (the JSON file is missing → create an empty `{}` first, so the failure lists every message).
- [ ] **Step 3:** Fill `serverErrors.json` with the en/de translation of every listed message.
- [ ] **Step 4:** Run the test. Expected: PASS. Add it to the suite.
- [ ] **Step 5:** Implement `translateServerMessage` and use it in `toErrorMessage`. Run build and lint.
